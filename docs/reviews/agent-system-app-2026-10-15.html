Call system services and develop real apps on the phone

This round verified two paths: the Agent calling Android system services, and the Agent writing Java, compiling and installing an APK on the device, updating it, then calling the new app business API. Experiments used only a dedicated emulator; no physical Pixel was operated.

1 · System service calls passedSettings Provider wrote/read the sleep timeout; Package Manager queried the package count; Sensor Service and Battery Service queried sensors and battery. Independent device readbacks matched, and settings were restored.
52 seconds · 10 real tool calls
2 · Source to native APK passedThe phone Agent wrote Java and a Manifest, then ran ECJ → D8 → aapt → signing → installation on-device. The APK contains real DEX, with no web assets or precompiled business-logic shell.
First version: 186 seconds · ordinary app UID 10151
3 · Edits, upgrades, and data retention passedScoring, undo, reopening after force-stop, and ordinary-app volume adjustment were tested. Upgrading to 1.1 retained A=2/B=0 and added a business API.
Second version: 117 seconds · replacement update with the same test signature
4 · Agent calls to the app API passedReal score/undo calls succeeded; invalid delta=0 was rejected with state unchanged. The open UI refreshed in sync without restarting the app.

The development environment still needs productization
The phone compiler toolchain and a new test signature were prepared separately, not preinstalled in the ROM or packaged as a cross-device installer. This small native app passed; that does not establish acceptance for arbitrary apps, all system permissions, a plugin marketplace, or physical hardware.
