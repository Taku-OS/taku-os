# Runtime cache and configuration concurrency: work in progress

Base: PR #13 at `eefc62777edb1d9bb9b5beeea7dbccbecfda1784`, with the launcher and test changes in this branch. This is an intermediate record, not acceptance of a release or a complete image.

On the dedicated Mac mini Android 16 ARM64 AVD `Taku_SkillsLifecycle_20261030`, the modified launcher was exercised with synthetic archives in an isolated temporary directory. The test checked that an executable old 0.161.0 cache is not used, eight simultaneous starts receive the new contents, changes to either archive select a new cache, damaged or incomplete cache contents and a truncated checksum list are rebuilt, abandoned extraction is removed, and an unsafe cache directory, lock symlink and invalid archive are rejected. The test removes its own temporary files. A separate contention probe confirmed Android mksh retains the Toybox file lock after the `flock` command exits. These tests do not execute the patched Codex binary or the GUI/broker product path.

The Android development components built successfully. `npm run verify` passed with JDK 21 and Python 3.14. The existing transaction host script passed 12 tests in an ARM64 Rust 1.95 container; those tests use a substitute configuration implementation and do not prove production TOML concurrency.

**Not accepted:** the standard image lock and bootstrap still select the upstream archive; a patched product artifact has not been built or integrated. Common configuration writes have not yet been safely integrated with transaction recovery. Review of a proposed shared-lock implementation found blocking lock acquisition on async workers while another task holds the lock across `await`, stale configuration loaded before journal recovery, and a remote cleanup decision made before acquiring the lock. Profile overrides and shared configuration aliases across different Codex homes also require explicit semantics. The candidate shared-lock implementation remains experimental and is not included in this PR. No final GUI/CLI product-path validation, Ready transition or merge has been performed.

Further review found that locking only the configuration and cache writes is insufficient for concurrent use of remote plugins: consumers retain plugin paths after the transaction lock is released. Replacing the cache can therefore change the files later read as skills, MCP or hooks. An experimental immutable-snapshot approach needs a safe cross-process lifetime and reclamation design: MCP subprocesses do not inherit the manager's lock descriptor, and skill paths may be read later in a session. Retaining every snapshot under a fixed cap would eventually block normal upgrades. The experiment also affects plugin execution attribution and path-based skill disable rules. It is not merged into this branch, has not passed product tests, and must not be treated as the fix.

The default product launcher uses one Codex home and the default configuration file. Cross-home aliases of one configuration file, profile-specific plugin configuration and read-only Codex homes have not been validated or resolved. Third-party MCP isolation remains outside the demonstrated guarantees. The PR remains draft and must not be merged until the requested runtime integration, configuration concurrency guarantees and real GUI/CLI acceptance are complete.
