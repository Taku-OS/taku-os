# Patched runtime and shared configuration lock

2026-10-31, Mac mini, dedicated Android 16 ARM64 AVD `Taku_SkillsLifecycle_20261030`. This record supersedes the outstanding delivery and configuration-lock status in [summary13](summary13.md), within the scope below.

The standard asset lock and bootstrap select [Taku's transaction runtime](https://github.com/Taku-OS/taku-os/releases/tag/taku-codex-0.161.0-tx-a137b21). It is built from OpenAI Codex `979011409de0a60b52f179721948e65531d26144` with the patch and transaction source at Taku commit `a137b217ab7c07e6fabfa75f589a1000be362826`. The ARM64 musl archive SHA-256 is `04c92b68ba495462a3e41588dc158dee0e2227efa8144c9e401e94d28e1b4e48` (102,404,511 bytes); its stripped executable SHA-256 is `bdcf5a816edb48d494577978762d0040dc6b448712aa36823b10ee34479b5650`. The build used Rust 1.95, the normalized pinned Cargo lock with `--locked --offline`, and prepared container image `sha256:fe7eb43bf66b76d429bfb9a5e7a913f6f0a33c23e29b9cffbfc0d838aed9fe36`. Bit-for-bit independent reproducibility has not been established. The release is private; bootstrap uses authorized GitHub CLI access and verifies both length and SHA-256 before replacing any cached file. The released file was downloaded again through bootstrap and matched the lock.

The actual broker-launched process resolved through `/proc/5047/exe` to the `runtime-v2` directory keyed by the new archive and code-mode host hashes, and its SHA-256 matched the executable above. After the interruption recovery below, `/proc/6860/exe` had the same digest. PID values are observations from this run, not stable identifiers.

General configuration writes, plugin configuration writes, marketplace configuration writes, and plugin transactions for the same `CODEX_HOME` use `CODEX_HOME/plugins/.lock` and recover any pending plugin transaction before the protected read-modify-write. Contention fails after 10 seconds. An async config write transfers lock ownership to the blocking persistence task so cancellation cannot release it while that task is still writing. The lock is advisory and does not serialize external editors or distinct Codex homes aliased to the same file. Reads are not snapshots.

Validation on the dedicated AVD and host:

- Three independent real patched app-server processes performed 20 rounds of install/uninstall concurrent with enable/disable and 40 distinct unrelated writes; every unrelated entry remained. A separate process held the same lock: a config write failed after 10.0 seconds and a subsequent write succeeded after release. Reproduce with `test-config-concurrency-device.py`.
- The product CLI installed, disabled, enabled and uninstalled the fixture, with MCP `hello` discovery and status checks. Actual GUI controls performed install, disable, enable and uninstall, each confirmed by CLI readback (`system/assistant/test-plugin-gui-lifecycle.py`).
- A separate patched app-server was SIGKILLed after the enabled-install journal committed and before the configuration write; restart restored both the installed cache and enabled entry while preserving an unrelated configuration entry (`test-plugin-install-kill-device.py`).
- During product CLI uninstall of a fixture with 20,000 files, the actual broker child was SIGKILLed after cache deletion began. The broker restarted and completed cleanup of cache, backup, journal and plugin configuration (`system/assistant/test-plugin-product-recovery.py`). This is process interruption, not a power-cut test.
- The launcher cache test checked old-cache avoidance, eight concurrent starts, archive changes, cache repair and unsafe input rejection. The transaction host suite passed 13 tests, including bounded lock contention and interruption/recovery cases. `npm run verify`, `npm run check:images`, and Android development component builds are separate checks; optional environment-dependent skips remain as reported by those commands.

**Known limitation:** plugin consumers may retain paths after loading; a concurrent install or uninstall may replace or remove the files later read by skills, MCP or hooks. The shared write lock does not provide immutable read snapshots. A separate PR is needed for snapshot lifetime and reclamation. Third-party MCP executes with the current runtime's privileges and is not isolated. The AVD result is not a physical-device, power-loss or full-ROM boot acceptance.
