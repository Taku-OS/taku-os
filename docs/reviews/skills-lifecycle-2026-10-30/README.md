# Skills lifecycle: version switching

A managed community skill's detail page can check its original GitHub source for a newer commit, install the checked revision, or switch back to the previously installed version. The receipt records the repository, source ID and path, commit, archive SHA-256, and SKILL.md SHA-256; older receipts can be updated only when their repository maps to exactly one current source. The check is repeated at installation time, so a changed source head requires another check. The existing SKILL.md is checked against its receipt before replacement. The previously active directory and receipt are retained outside Codex's skill directory, and uninstall removes that backup. The runtime is rescanned after a switch; the change applies to the next turn, not an already running turn.

On the dedicated Android 16 ARM64 emulator, the component test installed `openai/skills` at `e4131175b46f6aaf11d4b7b0df3b250fbfa58d5a`, detected and upgraded to `49f948faa9258a0c61caceaf225e179651397431`, checked native discovery, switched back, and checked receipt/hash and uninstall cleanup. The detail page was also used to check, upgrade, and roll back. The [detail screenshot](skill-version-detail.png) shows the checked revision and both actions; test logs are in the local lifecycle evidence folder; this is not a model-adoption test.

Known boundaries: switching recovers from ordinary operation failures but is not journaled against power loss or broker termination during filesystem renames; only SKILL.md is checked for local edits, not every resource in the directory. Plugin version switching and third-party process isolation remain unfinished. GitHub commit movement does not prove the selected skill's own files changed.

## Private GitHub sources

The source form can mark a repository private and accept or remove a repository-scoped token. The token is sent to the broker over its peer-checked local socket, never through the persisted task request. At rest it is a root-owned mode-0600 file in a mode-0700 directory; the source record and installation receipt do not contain the token. GitHub API calls use a bearer header, and the archive uses the authenticated GitHub zipball endpoint; redirects are restricted to approved HTTPS GitHub hosts. Network errors do not echo URLs, headers, or exception details. Missing credentials and rejected access have explicit messages.

The [source form](private-repo-form.png) and [missing-credential state](private-repo-missing.png) were inspected on the dedicated AVD. A synthetic token passed the device storage, removal, redacted response, rejected-authentication and task-record/log checks; public pinned installation and version tests were repeated with the GitHub archive API. No actual private repository or valid private token was supplied, so successful private GitHub download remains unverified. The token file is not hardware-backed or encrypted; root and code running with the broker's privileges can read it. It is not an isolation boundary against an untrusted root process.

## Native plugin and MCP fixture

The [official OpenAI packaging documentation](https://developers.openai.com/plugins/build/plugins) describes plugins as bundles of skills and MCP configuration; `.codex-plugin/plugin.json` is a supported compatibility format. The checked-in [local fixture](../../../examples/codex-plugin-lifecycle/README.md) uses that format on pinned Codex 0.161.0. On the dedicated AVD, `plugin/install` followed by `mcpServerStatus/list` reported the fixture's `hello` tool, and disabling then uninstalling removed it from MCP status. The [MCP tool list screenshot](plugin-mcp-tool.png) was inspected on the AVD. No model was called. The test installs an explicitly local sample with code owned by this repository; it does not validate third-party isolation. Unified plugin management, update and rollback remain unfinished.

On the lifecycle AVD, the native example server was observed as a root child of the root Codex app-server (`u:r:su:s0`). Consequently the existing native plugin workbench is not an isolation boundary: a third-party server could read root-private credentials or other runtime files. A disposable namespace probe confirmed that this emulator permits mount and network namespaces, but `unshare -p` returned `Invalid argument`; the prototype did not establish a complete process boundary and has not been shipped. Do not treat the example as evidence of safe third-party execution.


## Follow-up: plugin management and uninstall recovery

The extensions screen now presents the local runtime's workspace and home plugin catalog with install, enable/disable and uninstall controls. Install and uninstall require an in-drawer confirmation; a successful change requests an MCP reload. These controls were exercised with the repository's local fixture on the dedicated Android 16 emulator, including install, disable, enable and uninstall. The page displays a warning because the fixture's MCP process is still a root child. The catalog is scoped to the fixed `/data/local/agentos/work` working directory and sources visible to `plugin/list`; it does not yet provide source configuration, a complete inventory of orphaned installs, authentication flows for plugins requiring connector authorization, or plugin update/rollback. Version labels supplied by a mutable local source are not immutable version evidence. Codex 0.161.0's pinned protocol has install/uninstall/reconcile but no version-targeted update or rollback operation. A reliable implementation needs owned, content-addressed snapshots of the complete plugin and its marketplace metadata, validation of the active tree, a transaction journal, serialized config and MCP reload, and native discovery checks before offering rollback; reinstalling an unpinned source alone cannot provide those properties.

Managed community-skill uninstall now persists intent before changing configuration or detaching files. On next app-server initialization or skill management request, the broker repeats the pending operation through native rescan, selection and receipt removal, and cleanup. The detached directory is next to Codex's skill directory: Android's app-private directory and runtime directory can have different encryption policies even on `/data`, so cross-directory rename failed on the test AVD. Conflicting or missing paths stop recovery instead of deleting an unexpected tree. An admission barrier blocks new native execution requests while skill management runs, and pending or realtime requests block management; the existing active-turn check remains. Component tests simulate interruption before detachment, after detachment including a disabled skill, and after receipt removal, then repeat recovery. They also recovered the actual failed cross-directory attempt. The admission test checks both directions. This covers broker/process interruption, not sudden power loss: directory metadata is not explicitly fsynced, and no power-cut test was run. Externally modified files, plugin operations and the earlier skill version-swap transaction are outside this journal.

## Third-party MCP isolation proposal

The current root Codex process directly spawns commands from plugin MCP configuration; an optional wrapper or a user-editable manifest is not an enforceable boundary. A production design should put every untrusted stdio MCP server behind a broker-controlled Android isolated service with a distinct isolated UID and SELinux domain, never sharing the root runtime home, authentication files, inherited environment or privileged file descriptors. Copy a verified immutable plugin snapshot into a read-only area for that identity; expose only a bounded per-plugin scratch directory. A broker-owned stdio proxy mediates requests, process lifetime, output size, resource limits, cancellation and explicit network policy. Installation must reject arbitrary direct command launches outside that proxy and fail closed when the sandbox cannot be established. Treat remote HTTP MCP separately with per-origin credentials and network policy. Validate with adversarial servers attempting to read private credentials, access other plugins and workspace paths, open sockets, retain descendants and exhaust resources; verify denial and ordinary tool discovery/calls on emulator and physical devices. Android isolated-service packaging, SELinux policy and the native Codex launch integration still need implementation and testing. No privilege reduction or security isolation is claimed in this PR.

## Follow-up: network and native uninstall probe

On the dedicated Android 16 ARM64 lifecycle AVD, the phone-local HTTP proxy was reconnected to the host proxy with ADB reverse. The first retry reached GitHub but failed with HTTP 403 because the shared anonymous API quota was exhausted; a later retry succeeded. The complete `test-skill-uninstall.sh` run passed, including public `openai/skills` installation at `49f948faa9258a0c61caceaf225e179651397431`, native discovery and removal, version switching and recovery, and the synthetic private-credential checks. This does not validate a real private credential or model adoption. The AVD's runtime files and reverse mapping were restored temporarily and do not survive reboot.

A separate exploratory probe issued two overlapping `plugin/uninstall` requests for the local fixture on one app-server, five times. Both requests returned success in each round and the fixture was absent after reload. This observation does not establish serialization across app-server processes or recovery after interruption, and it does not test uninstall against a concurrent install or active tool call. In the pinned upstream source, local uninstall removes the plugin store first and clears its user configuration afterward; process death between those steps is not covered by this probe. The stdio MCP transport directly spawns the configured command. The isolation proposal above therefore remains unimplemented and the root warning remains applicable.
