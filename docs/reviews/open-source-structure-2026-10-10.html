Five concrete gaps before open source

01

ROM builds remain outside the repository

The main entry only compiles APK/JAR. A neighboring experiment directory holds Docker/Lineage builds, pinned manifests, image export, and boot scripts using machine-specific absolute paths. External developers cannot build the complete Taku OS by cloning this repository alone.

Both experimental full-Lineage logs and the container indicate successful completion and record an emu64a image ZIP path; however, the script includes only the Settings overlay, not all current Taku system components. The ZIP itself and cold boot were not verified this round.

Evidence: scripts/build-android.sh:8; docs/project-structure.md:3; experimental linux-build/build-rom.sh and rom-build.log
02

Installation and UI checks still depend on a particular experimental AVD

Several scripts hard-code emulator-5582 and AgentOS_ImageCheck. No ADB device is currently connected. Standardize explicit device parameters, target-capability checks, artifact manifests, and post-install checks so contributors can use matching environments of their own.

Evidence: system/assistant/install.sh:5; system/overlay/deploy.sh:5; system/assistant/test-*.sh
03

CI does not cover Android or image layers

Current CI checks protocol/catalog/historical evidence and app-kit APIs. Add Android-component builds with a pinned toolchain, then a separate image job and cold-boot acceptance. Successful Android compilation cannot replace device runtime results.

Evidence: .github/workflows/ci.yml:17; npm run verify and npm run build:android both exited 0 this round
04

The current license is not an open-source distribution license

LICENSE authorizes only internal-member development and explicitly does not authorize redistribution or publication; CONTRIBUTING also remains internal. Before publication, determine the original-code license and verify upstream, font, icon, desktop-pet, and screenshot provenance/distribution scope individually. NOTICE, LICENSES, and REUSE.toml are a foundation, not proof of a complete license audit.

Evidence: LICENSE:6; NOTICE; REUSE.toml · No license changes, public repository publication, or full REUSE check this round.
05

Dependency pinning and initial device setup remain incomplete

Codex and app-kit downloads pin versions, but their scripts do not verify artifact SHAs; native-device Node, packaging tools, and signature preparation are not unified. Define reproducible dependency inputs and device bootstrap before distributing artifacts.

Evidence: adapters/codex-runtime/bootstrap.sh:6; tooling/app-kit/bootstrap-dependencies.sh:6; tooling/app-kit/README.md

Recommended minimum evolution

taku-os/
├── system/             Keep custom system implementations
├── core/ · sdk/ · spec/ Keep protocols and interfaces
├── adapters/           Keep engine/transport adapters
├── tooling/            Keep generation and diagnostics
├── rom/                Add when implementing image integration
│   ├── manifests/      Pin upstream revisions
│   ├── products/       First ARM64 emulator product
│   └── sepolicy/       System policies actually required
├── scripts/            Build/install/boot/acceptance
└── docs/ · tests/ · evidence/

Keep the full AOSP/Lineage checkout in an external build directory.
Add physical-device device/vendor/kernel trees as needed.
Do not commit images or private keys to Git.

Use centrally maintained custom code + manifests pinning upstream. The complete Android source need not be copied into the main repository, nor should more components automatically trigger splitting into many repositories.

  1. Move reproducible ROM build logic into the main project and choose the first emulator product.
  2. Include current system components in an actual product image; track boot, permissions, and default Home/assistant configuration as integration inputs.
  3. Cold-boot a new AVD without personal sign-in; accept Home, TaskBroker, background display, and device CLI.
  4. Record source SHA, upstream manifest, toolchain versions, artifact SHAs, and boot results.
  5. Then choose the first physical device and implement its flashing/recovery paths.

These are proposals: no placeholder directories were created, and no image or hardware acceptance is claimed.
