How to implement this in the current project

  1. First implement a device deployment entry.Explicitly select the Pixel serial and tokay; check build version, certificate, APK version code, and current task state; choose app / broker / display components.
  2. Reuse existing component builds.bash system/assistant/build.sh produces APK and broker JAR; bash system/display/build.sh produces display JAR. Existing install.sh hard-codes an emulator and must not be used directly on Pixel.
  3. Handle version code before APK updates.The preinstalled phone APK has versionCode=36; the local script has no explicit version. Set an appropriate development-APK version rather than replacing solely on signature match.
  4. Use the official remount path for JAR updates.After verification, push only selected Taku files and restart the corresponding services; do not run whole-device adb sync every time. Deploy APKs and JARs together if their protocol changes.
  5. Produce reviewable results for every deployment.Record source digest, artifact SHAs, device package paths, service PID / UID, screenshots, error logs, and real-task results. Retain previous components and preserve account, conversation, and task data.
  6. Return to image acceptance before release.Put verified changes into a pinned build snapshot, remove development overlays, install the candidate OTA, then test cold boot and real Agent tasks.

This is a plan and device-prerequisite check; one-command deployment, file watching, and physical-device component replacement are not yet implemented / accepted.

Two meanings of “hot reload”

Fast deployment without flashing:Feasible. Automatically compiling, replacing, and restarting an app or service after saving source is the most direct development loop for this Java View + APK / JAR project.

Code replacement while retaining the process:Android Studio Apply Changes supports some edits but requires a debuggable APK and compatible project/deployment environment. This custom aapt2 / javac / d8 build does not mark the app debuggable and does not use Compose, so Apply Changes / Compose Live Edit are not existing capabilities. Manifest, field, and method-signature changes still need a restart.

A development-only debuggable build can be added later without first migrating the UI stack. Fast APK / JAR deployment usually already avoids full-ROM build and flashing steps.

System synchronization and OTA cautions

Official adb remount / OverlayFS supports development overlays on read-only partitions. Initial setup may require disabling verity and rebooting before pushing files. Remove overlays before OTA acceptance: otherwise executed files may differ from the image, and OverlayFS affects OTA.

Incremental OTA reduces transfer size but still needs new artifacts and a reboot; it is not hot reload. It requires exactly matching old and new target-files.

The special baseline of this Pixel:The installed image is a partial OTA retaining existing boot firmware and baseband; the original October 11 target-files contain older firmware. For incremental OTA, record and verify the actually flashed target state rather than assuming every partition matches the original target-files.
