# Starter contribution task drafts

The following 10 documentation tasks can be broken down further into Issues. They do not imply that GitHub Issues have been created, external contributors have claimed them, or the tasks are complete. First read the [contribution guide](../CONTRIBUTING.md) and [first change](first-change.md).

For each task, the claimant first supplies a minimal change and evidence, then the relevant module maintainer reviews it. Specific reviewers are determined by [CODEOWNERS](../.github/CODEOWNERS) and explicit ownership in the Issue. Roles in the table are suggested responsibilities, not commitments made on anyone's behalf.

| # | Task and files | Prerequisites | Deliverable and completion criteria | Suggested responsible role |
| --- | --- | --- | --- | --- |
| 1 | Reproduce [first change](first-change.md) in another clean environment | Node 22+, repository access; no phone required | Record OS, Node, source SHA, both commands and results; correct documentation if they differ. This proves only the offline metadata path | Documentation contributor; SDK maintainer reviews |
| 2 | Review the Linux environment instructions in [getting started](getting-started.md) | Python, JDK 17+, applicable Android SDK | Check environment variables, dependencies, and failure messages; state the actual execution scope. Do not misreport missing dependencies as feature failures | Linux developer; build maintainer reviews |
| 3 | Review the macOS environment instructions in [development](development.md) | A usable macOS development machine and toolchain of your own | Check path discovery and dependencies, provide copyable commands, and avoid personal absolute paths or caches | macOS developer; build maintainer reviews |
| 4 | Add error-troubleshooting examples to the [SDK protocol](protocol.md) | Understand the existing protocol and `core/`; read-only code inspection | Choose actual parameter-error/missing-transport cases and record real responses and error codes without creating protocols or features | SDK documentation contributor |
| 5 | Review JVM examples in the [plugin documentation](plugins/README.md) | Bash 3.2+, JDK 17+, using only local test directories | Verify commands, generated package types, state files, and errors; clarify that JVM JARs are not Android DEX, without changing Android installation state | Plugin contributor; plugin maintainer reviews |
| 6 | Add dependency troubleshooting to the [RN app guide](../system/agent-app/README.md) | Node ≥22.18; follow that directory's AGENTS | Verify one actual installation/lint/typecheck issue and solution; do not treat Expo Go as a native-gateway environment | RN developer |
| 7 | Check navigation and terminology across the three-language READMEs | Able to proofread at least two corresponding languages | Align capabilities, version scope, and links in `README.md`, `README.zh-CN.md`, and `README.ja.md`; do not translate goals into completed features | Bilingual documentation contributor |
| 8 | Review one source in the [third-party materials inventory](third-party-materials.md) | Access to the corresponding pinned upstream version and license text | Add pinned origins, modification scope, and packaged notices; correct information only, without changing upstream licenses or asserting trademark rights | Provenance reviewer; maintainer confirms |
| 9 | Proofread one implemented interface in [Agent open access](agent-open-access.md) | Understand the owning code; runtime work requires your own isolated AVD | Check parameters, errors, and authoritative data against preinstalled documentation; if testing on-device, record both GUI↔command directions and versions | Android documentation contributor |
| 10 | Prepare one reproducible Case script for [launch assets](launch-assets.md) | Specified version and usable device, with test materials approved for publication | First deliver steps, expectations, permissions, Agent commands, and failure boundaries; after recording, add the actual device/version. Do not present synthetic images as real testing | Case author; module maintainer and design collaborator review |

Documentation changes may first pass local structural checks. Actual new settings, feature fixes, or UI changes should be separate engineering tasks following the device-acceptance requirements in [AGENTS.md](../AGENTS.md). Before public recruitment, maintainers should create, assign, and appropriately label real starter Issues.
