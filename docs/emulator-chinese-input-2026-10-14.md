# Troubleshooting Chinese input in the emulator

## 2026-10-29: GUI acceptance environment and host keyboard

Newly copied AVDs also inherit `hw.keyboard=no`. The repository now provides a launcher requiring an explicit AVD and port:

```sh
python3 scripts/start-emulator.py --avd YOUR_AVD --port 5590 --writable-system
```

It sets `hw.keyboard=yes` for the selected AVD and saves
`config.ini.before-host-keyboard` in the AVD directory before the first change; it uses hardware GPU and cold boot without clearing userdata.
It refuses to start if the same AVD is already running or a device on the same port is connected, without stopping other devices.
`--configure-only` prepares configuration only; an already-running device still needs a cold restart for it to take effect.
The script does not install APKs or automatically deploy the current branch to the device.

In the native Android Emulator, the Mac Command key simulates multitouch; green dots and connecting lines indicate that mode, not Taku cards or input controls.
Release Command, then click the text field to type.
To pass shortcuts to Android, select the virtual device in emulator `… → Settings → General → Send keyboard
shortcuts to`. Android paste usually uses Control+V or a long press in the field followed by Paste;
do not assume Command+V works as paste in every emulator window.
Host/device clipboard behavior also depends on the Emulator Clipboard Sharing setting.
Enabling a hardware keyboard does not establish support for forwarding Mac Pinyin candidates; Chinese-input validation boundaries are below.

ChatGPT browser authorization does not require typing passwords through the emulator keyboard: open the official authorization URL just generated by the device runtime in a browser on the same computer.
If the URL's `redirect_uri` is
`http://127.0.0.1:1455/auth/callback`, first create callback forwarding for the explicitly selected device:

```sh
adb -s emulator-5590 forward --no-rebind tcp:1455 tcp:1455
# Remove this forwarding after completing or canceling authorization:
adb -s emulator-5590 forward --remove tcp:1455
```

Do not restart the device while forwarding remains active. If the port is occupied, stop and inspect rather than overwriting another login session.
Use the URL generated by this device for this attempt; ordinary ChatGPT web login does not connect the device runtime.
The URL is only for local authorization and must not enter the repository or acceptance screenshots; the user enters passwords and verification codes on the official page.

References: [official emulator operations](https://developer.android.com/studio/run/emulator),
[keyboard-shortcut settings](https://developer.android.com/studio/run/emulator-extended-controls).

## 2026-10-19: direct MacBook input verified

A separate local `~/Applications/Taku Simulator.app` entry was added; existing `taku-emulator mirror` also uses it. A small patch to official scrcpy 5.0.1 forwards non-ASCII text committed by the Mac input method through SDL to the existing Android clipboard + PASTE protocol. The user confirmed direct Chinese input with a physical keyboard and WeChat input method; reads from the native Android test control also contained the actual committed Chinese text. Uncommitted Pinyin and candidate windows remain on the Mac.

The patch, pinned upstream commit, rebuild/installation scripts, fallback copy, and acceptance records are together in `~/.local/share/taku-devtools/host-ime/`, with maintenance instructions in its `README.md`. Homebrew scrcpy remains unchanged; `taku-emulator mirror --official` opens the official build. Closing the mirror window does not stop the AVD; if the AVD is stopped, the app uses the existing launcher to start the same AVD headlessly.

Automatic clipboard sharing is disabled at both endpoints so input-method commits are not copied back to the Mac clipboard. Android's clipboard retains the last non-ASCII commit; password fields or custom controls that reject paste are outside the verified scope. No Android Chinese input method or global keyboard hook was installed. The test APK was removed. Synthetic automated key events did not open Mac input-method candidates, so actual IME acceptance used the user's physical keyboard and native-control readback; automated key events cannot substitute for that evidence.

## Original investigation background

The dedicated AVD had only AOSP LatinIME, no Chinese Pinyin input method, and hw.keyboard=no in config.ini. Taku EditText received and displayed Chinese correctly. Android SDK key-based text injection maps Unicode characters back to keyboard events and drops unmappable characters. This is consistent with host Chinese candidates failing to enter the original emulator window, but the documented behavior was not treated as a full reproduction of the macOS GUI issue.

## Verified scope and boundaries on 2026-10-14

The real Android ClipboardManager → KEYCODE_PASTE → Taku composer test passed, preserving Chinese, punctuation, and Emoji in 4.85 seconds. The original draft and device clipboard were backed up in memory and restored, without sending test content to the model. Screenshot: out/emulator-input-test/unicode-paste.png.

On-device paste was verified; direct Mac input-method candidate forwarding and the complete Mac-clipboard path through scrcpy had not yet passed automated acceptance, so direct input could not be called fixed. The test did not install an input method, change system language, restart the emulator, or modify a physical phone.

## Manual paste with official tools

Use the installed official scrcpy 4.1 to control the dedicated emulator, type/copy Chinese on the computer, click the phone chat composer, then press Command+V. Explicit MOD+V synchronizes the clipboard and invokes Android PASTE; do not use Command+Shift+V or legacy-paste, whose character-to-key conversion can corrupt non-ASCII text. A separate control window was started; closing it does not stop the AVD.

```sh
scrcpy -s emulator-5634 --force-adb-forward --no-audio \
  --no-clipboard-autosync --shortcut-mod=lsuper,rsuper,lalt \
  --window-title 'Taku OS - Chinese paste window' --max-size=1280
```

Disabling automatic clipboard synchronization retains explicit manual MOD+V while avoiding continuous reverse synchronization. For continuous Pinyin typing, select a Chinese input method in Android and use scrcpy -K / --keyboard=uhid to send physical keys to it; candidates come from the phone, and the Mac should remain in ABC/English key input. This combination is not installed or accepted here; enabling hardware keyboard alone does not provide a Chinese engine.

Optional open-source Chinese input methods for the image include Trime RIME and Fcitx5 Android. Bundling them in a ROM requires separate license, architecture, dictionary, actual-keyboard, and background-screen acceptance; a host debugging window is not a phone-system component.

## v49 background phone-tool input

`taku_phone.type_text` uses `PhoneTextInput` to enter Unicode text on an independent execution screen. It selects the unique valid focus in the target display's app window; without editing focus, it accepts only a unique editable field. Multiple candidates, uninspectable windows, or foreground display IDs return explicit errors. It rereads text after writing to detect truncation by input filters; it does not change foreground focus or install a Chinese input method.

A dedicated test APK supplies independent foreground/background text fields and verifies results through text/focus recorded by the controls themselves. Tests cover Chinese, punctuation, Emoji, newlines, single/multiple fields and windows, and input-filter failures. The APK is installed only for testing and removed afterward.

```sh
bash system/assistant/build-phone-input-tests.sh
# First read the existing independent display ID: adb -s emulator-5634 shell /system_ext/bin/phone-display id
python3 scripts/test-phone-text-input.py --serial emulator-5634 --display 2 --installed-broker
```

`--installed-broker` verifies the device JAR against the local build SHA and calls the production entry and its time-limited subprocess. Records are in `out/phone-input-tests/`. These tests verify background tool input, not direct Mac Pinyin candidate forwarding, third-party input methods, or every third-party app's editing controls.

The six scenarios passed on 2026-10-18, with foreground text/focus unchanged and the test APK removed. `classes.dex` matched byte for byte between final build and tested JAR; wrapper JAR hashes are separately recorded in the [v49 acceptance record](../evidence/builds/2026-10-18-composer-reliability.json), with foreground/background screenshots in `evidence/scenarios/composer-2026-10-18/`.
