Boundaries of this build

The device tree declares vendor baseline BP4A.260205.002 / 2026-02-05. Do not flash old boot firmware onto a device with unknown firmware. This build uses development userdebug; the upstream su domain is permissive, and global Enforcing does not mean this service domain is enforcing.

Gemini and Pixel Launcher are excluded from the selected product packages. The upstream recents provider remains temporarily; Taku HOME is integrated, but complete gestures and recents are unverified.

Compilation, ZIP verification, flashing, cold boot, and actual-task acceptance are separate gates. This page shows the actual build stage and does not present an ongoing build as a finished artifact.

Acceptance sequence after arrival

Updated 2026-10-11 · Preparation checklist; none of the physical-device steps below has run. The candidate package has been exported.

  1. Confirm the device:Select only this user-owned Pixel 9; verify tokay codename, capacity, current Android/build/SPL, and BL state; record the active slot and boot-firmware versions. Do not operate other connected devices.
  2. Confirm firmware compatibility:Align device firmware with this candidate vendor input BP4A.260205.002 and check rollback restrictions. Android version or SPL date cannot replace boot-firmware inspection; adjust the build baseline if compatibility cannot be confirmed.
  3. Preserve a recovery path:Back up new user data, prepare the matching official tokay recovery package and SHA, and confirm access to bootloader and recovery modes. Factory-image restoration erases data; this candidate has not passed production-signing or relocking acceptance.
  4. Verify one artifact batch:Full target-files, OTA, and partition images must come from one build and pass CRC, tokay-property, SHA, and Taku-package checks. Upstream tokay uses vendor_boot for recovery and also needs matching boot, dtbo, and vendor_kernel_boot; actual installation steps will be determined after inspecting the finished artifacts and device.
  5. Accept the system first:First boot, power-off cold boot, and another reboot; inspect touch, Wi-Fi, camera, audio, fingerprint, charging, and standby before Agent acceptance.
  6. Then accept Taku:Home/assistant roles, three-service startup after unlock, actual background rendering and targeted input, main-display focus, IME, video, service stop/recovery, DNS, and real tasks. The program archive contains no sign-in state; networked Agent tasks need separate acceptance.
  7. Finally accept updates and recovery:Clarify both slot states; verify the next candidate OTA, data retention, and failure recovery before discussing production service domains, signing, and relocking. Keep the current permissive development su domain explicitly recorded in acceptance results.
