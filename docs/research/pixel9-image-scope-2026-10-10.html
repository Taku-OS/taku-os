Stock experience and full source control

Test hardware first: stock Pixel base + Taku runtime

Follow the existing baseline research, prioritizing stock drivers, camera, SystemUI, and lock screen. Privileged services host the Agent and background display; Taku replaces the Gemini and Pixel Launcher entry points and completes recents/gestures.

The development package must match phone boot images and root bootstrap. This is not yet a fully rebuilt Taku ROM and does not give us complete control over the stock framework.

Framework changes: tokay source ROM

When focus, power, system services, or SystemUI need changes, use a Pixel 9 device build integrating the same Taku components, custom platform signing, init, and SELinux policy.

Official LineageOS device metadata currently lists 23.2, requiring Android 16 firmware before installation. This source candidate is not yet pinned or built; it is not stock Pixel OS and cannot mix arbitrary Android 17 vendor inputs.

Custom images may change Play Integrity; payment, banking, and DRM apps need separate acceptance. Public vendor binaries also have their own use/redistribution terms; opening Taku source does not automatically permit public distribution of a complete ROM containing them.

What the existing repository still lacks

  • Complete AOSP/Lineage repo manifests and pinned source commits.
  • A matching tokay product/device/vendor/kernel combination and dedicated artifacts.
  • Home currently declares android.uid.system and uses the public AOSP test platform key; stock Pixel will not recognize it as a Google platform-signed app.
  • Components have independent build records; only the Settings overlay has Android.bp, while the others need ROM-build, init, permissions, and sepolicy integration.
  • DisplayHost silently sets critical reflected flags to 0 on failure; the background display lacks independent boot startup, and the mirror socket permits only UID 0/1000/2000.
  • Production signing, complete flashing/recovery packages, OTA chain, and Pixel cold-boot acceptance.

When can it be called “flashable on Pixel”?

  1. Pinned version combination:Read tokay, system build, and BL unlocked from the actual phone; pin source, vendor/firmware, kernel, and artifact SHAs. The newest stock monthly build is not automatically a rebuildable baseline.
  2. Successful cold boot:First verify the device baseline, then add Taku and cold-boot into Taku Home.
  3. Working hardware:Photo/video, network, Bluetooth, calls, fingerprint, audio, location, charging, sleep, and power use.
  4. Taku core passed:Agent starts without a computer; tasks recover after reboot and first unlock; foreground/background input does not steal focus; target apps, IME, and video are accepted individually.
  5. Updates and recovery passed:Stock restoration, both slots, and update behavior are recorded. Releases use production keys; relocking a custom ROM requires separate AVB/custom-root-of-trust verification and must not be done directly.
