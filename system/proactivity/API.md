# Proactivity public protocol v1 and Android SDK

Status: 0.1 implementation, Android API 36. Requests follow the [JSON Schema](../../spec/proactivity-v1.schema.json); field implementations are [ObserverSpec](contract/org/agentos/proactivity/api/ObserverSpec.java) and [ProactivityWire](contract/org/agentos/proactivity/api/ProactivityWire.java). Only `settled_event` is implemented. The general registry, model adapters, and Agent tools in the [overall design](../../docs/proactivity-trigger-design.md) are outside this public API version.

## Connection and identity

Explicitly bind `org.agentos.proactivity/org.agentos.proactivity.ProactivityService` with `BIND_AUTO_CREATE`, then wrap the returned Binder in an Android `Messenger`. The plugin manifest declares the host package in `<queries>`. Plugins use their own signatures, package names, and UIDs. An Activity may additionally declare `org.agentos.proactivity.OBSERVER_PLUGIN` in an intent-filter for discovery; this grants no permissions.

Each request uses `Message.what=1`, a client Messenger in `Message.replyTo`, and a JSON string in the Bundle's `payload`. `Message.sendingUid` determines the package, currently installed versionCode, and signing SHA-256. The payload cannot claim a UID, source package, signature, or authorization state. One UID must map to exactly one package and one signature; shared UIDs and multiple signatures are currently rejected. Registration pins the current signature. Signature rotation is unsupported and requires explicit removal and re-registration by the user.

Replies use `Message.what=100` and the same Bundle `payload` field. Clients must verify that `message.sendingUid` belongs to the target host package and check the protocol version. The optional SDK performs these checks. They depend on the installed host identity; distribution must also verify the trusted host signature. The host has no private plugin entry point beyond the SDK protocol.

## Requests

```json
{
  "version": 1,
  "requestId": "07f5088b-7e1e-4007-a5a8-e05abeab48a8",
  "op": "register",
  "args": {
    "spec": {
      "id": "org.example.taku.observer.page",
      "name": "Page settling observer",
      "eventType": "org.example.taku.observer.page_changed",
      "quietMs": 700,
      "cooldownMs": 1500,
      "maxRecords": 8,
      "lookbackMs": 120000,
      "title": "Page settled",
      "summary": "Would you like to view it?"
    }
  }
}
```

The outer object has exactly four fields; `args` is validated strictly for each operation. `requestId` is a lowercase UUID; the implementation checks 36 characters from `[a-f0-9-]`. Unsupported versions or operations are rejected without fallback interpretation. Requests are limited to 16 KiB of UTF-8 and 16 nesting levels. Numbers must be integer JSON numbers; numeric strings are rejected.

| Operation | `args` | Result |
| --- | --- | --- |
| `capabilities` | `{}` | `version=1`, `observerKind=settled_event`, at most 4 observers per package, at most 16 context records, `promptTypes=["hint","choice"]`, `promptActionIds=["accept","cancel"]`, `imageDecision=false`, `agentExecution=false` |
| `register` | `{spec: ObserverSpec}` | Saves or idempotently returns the caller's registration state; new or changed declarations and installed code version changes await user confirmation |
| `event` | `{observerId,eventId,eventType,pageRevision}` | `{accepted,duplicate,policyRevision,producerCodeVersion}`; accepted here means the event entered the queue, distinct from a user tap callback |
| `inspect` | `{observerId}` | Returns only the caller's registration, authorization, policy history, and bounded activity records |
| `disconnect` | `{}` | Unsubscribes this caller's current reply Binder and revokes its pending candidates and hints; returns `{}` |

The state returned by `register/inspect` includes `package/id/signer/approved/enabled/activeRevision/pendingRevision/history/registration/trace/lastOfferWall`. Each `history` entry has `revision/codeVersion/spec`; user edits include `author=user`, and rollbacks include `rollbackOf`. Revisions are increasing integers generated by the host. `registration` retains the original spec and codeVersion from the last plugin request, separately from the user's effective policy. A client must not use `approved` in a registration response to bypass `pendingRevision`.

### Field constraints

`id/eventType` match `[A-Za-z][A-Za-z0-9_.-]{2,119}` and must start with the actual calling package name followed by `.`. Events must use the declared type; they cannot impersonate the system, another plugin, or business records. `eventId` uses the same identifier format and deduplicates within the current bounded record window. `pageRevision` is 0–2147483647 and represents only the plugin's local page revision, not proof of system window identity.

| Spec field | Bounds and meaning |
| --- | --- |
| `name/title/summary` | Nonblank text, at most 80/80/240 Java UTF-16 code units respectively. Schema character lengths are a static precheck; host validation is authoritative. |
| `quietMs` | 100–10000 ms; each new event resets the settling wait |
| `cooldownMs` | 1000–3600000 ms, measured from the display layer's actual publication ACK. Events during cooldown are not automatically delayed and replayed; a later new change is required. |
| `maxRecords` | 1–16; maximum selected context records |
| `lookbackMs` | 1000–600000 ms; event lookback window when settling triggers |
| `prompt` | Optional `{acceptLabel,declineLabel}`, each nonblank and at most 80 Java UTF-16 code units. No other prompt fields are accepted. Omit it for the original single `Viewed` hint. |

An approved `prompt` uses the existing Surfaces choice renderer as an initially expanded top card. Its decline and accept action IDs are fixed to `cancel` and `accept`; labels can read `Not now` and `Try on`. Card-body taps do not accept it. The declaration cannot specify an intent, service, arbitrary action target, placement or execution. Registering a prompt or changing either label creates a pending policy revision and suspends offers until that revision is approved. The original nine-argument Java `ObserverSpec` constructor remains available; the ten-argument overload takes nullable `PromptSpec` as its final argument. A missing prompt serializes to the original nine fields; explicit JSON `null` is rejected.

Limits are 32 observers overall and 4 per package. Each observer has at most 64 in-memory metadata records, 8 policy revisions, and 16 persisted activity records. The persisted store is limited to 256 KiB; exceeding it rejects the write and preserves the previous state. Each UID may send at most 240 requests per minute, with at most 128 active rate-limit buckets. The event UI example does not authorize unlimited per-keystroke uploads. At most 8 candidates may await publication at once.

## Replies and asynchronous callbacks

Successful request: `{version:1,ok:true,type:op,requestId,result}`.
Failed request: `{version:1,ok:false,type:op,requestId,code,message}`. Early parse failures may leave `type/requestId` empty. Codes are `not_authorized`, `rate_limited`, and `invalid_or_unavailable`. The message explains the check failure; application logic must not depend on its exact wording. Frames lacking replyTo, with the wrong what, or without a valid sendingUid are ignored.

Asynchronous messages use `{version:1,ok,type,result}`, without requestId. Clients should reread the effective policy after `policy_changed`. A registration response does not mean a hint has appeared.

| Callback type | Meaning |
| --- | --- |
| `policy_changed` | State successfully persisted after user approval, disabling, adjustment, or rollback |
| `published` | Actual Surfaces publication ACK; starts the hint cooldown |
| `accepted` | User tapped `Viewed` or the declared accept button; the host rechecks policy and candidate validity, revokes the offer, then sends one callback. Only `promptType=choice` with `actionId=accept` identifies acceptance of a declared choice. |
| `dismissed/expired/error` | Display-layer removal or error callback, not a task execution result |

Hint-related results contain `candidateId/observerId/policyRevision/sourcePackage/producerCodeVersion/records/promptType/imageDecision/agentExecution`. `promptType` is `hint` for legacy `Viewed` and `choice` for a declared prompt. Action callbacks additionally contain `actionId`; accepting uses `accepted` plus `actionId=accept`, declining uses `dismissed` plus `actionId=cancel,reason=declined`. Display-layer dismissals without a button do not imply either action. Consumers that require a real choice must check `accepted`, `promptType=choice`, and `actionId=accept`; neither old `Viewed` callbacks nor missing `promptType` authorize that choice. All action callbacks validate the offered policy revision and freshness, and withdraw before another tap can be handled.

Record fields are `id/type/sequence/observedAt/pageRevision`. The host generates `sequence` and `observedAt`; time is elapsedRealtime milliseconds within the current boot. `sourcePackage` comes from Binder ownership, and `producerCodeVersion` is the actual installed version, never fabricated from old policy history. Model decisions and execution capabilities are fixed to false.

Selection order: restrict to the current observer and type → use the host's monotonic event receipt time → deduplicate IDs and enforce the 64-record bound and lookback window → take the latest N records when settled → freeze in ascending sequence order. If fewer than N exist, return the actual count; do not add bodies, other apps' records, or later events. New events, disconnection, Binder death, lock screen, and policy changes invalidate old candidates. Publication requires an unlocked, interactive screen. Candidates have a 120-second TTL; publication and acceptance revalidate versions, context generation, and device state.

Deduplication and context are temporary in-memory facilities. Historical eventIds may no longer be deduplicated after disconnection or process restart. This API is not a persistent queue or global event bus. Failed candidates and events skipped because of locking or cooldown are not automatically replayed; a new valid event is required.

## Users, AI, and revisions

Authorization is performed only in the host's own Activity. External `approve/disable/rollback/apply` operations do not exist. Extras can navigate but cannot grant access. Approval and rollback are bound to the expected policy revision shown to the user; an intervening update rejects the stale action. An installed plugin version change rejects events even if the plugin skips register. Publication and acceptance also recheck signatures and installed versions. Users can adjust settling delay, hint interval, maxRecords, and lookbackMs directly. Saving checks expectedRevision; an intervening policy update rejects stale edits, and failed writes preserve the old state. The editor retains `prompt` exactly; the registry rejects adding, removing or relabeling it through timing/context edits. Prompt changes use registration and fresh approval. Enabling/disabling, editing, and rollback immediately invalidate old candidates.

A plugin or AI modifying an observer it owns submits a new spec through the same `register` operation. This creates a pending revision that takes effect after user confirmation. Repeating the same code version and spec is idempotent and does not overwrite user edits or rollbacks. New specs or code versions require confirmation again. Field-level merging of user overrides is not implemented; users should compare parameters before confirming. Cross-plugin AI policy tools, generic patches, simulation replay, import/export, and conflict previews are future interfaces, not callable v1 methods.

Policy rollback restores the earlier policy's parameters and copy in a new revision. It does not install or downgrade an APK. The example's `adb install -r -d` downgrade is accepted only on debuggable test packages. Even a code downgrade independently creates a pending registration. User-data retention depends on Android installation behavior and plugin compatibility.

The host commits with AtomicFile and publishes in-memory state only after success. Authorization, history, and the wall-clock time of the last successful hint persist. Recovery converts that time to a monotonic cooldown for the current process. Significant system clock changes produce a conservative cooldown, not scheduling data. Pending candidates, Binder subscriptions, and event records do not recover across processes.

## Optional SDK

`system/proactivity/out/taku-proactivity-client.jar` contains only the contract and Android client. Create it and call connect/request/close on the main thread; listen for `onConnected/onMessage/onDisconnected`. Developers may use Messenger directly according to this protocol without depending on the JAR. See the [independent observer](../../examples/proactivity-observer/README.md). The host implementation, Memory, Assistant, and platform signature are not plugin compilation dependencies.
